# Plan 03: Dine-in and KDS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the contactless dine-in path (table signature, session, cart, station-routed KDS tickets, bill split, dynamic UPI shares) and the kitchen display (timers, load, bump actions, live SSE updates), with the two pages Route 1 and Route 3.

**Architecture:** Pure rules (`lib/dine/`, `lib/settlement/`, `lib/kds/`, `lib/menu/`) have no I/O and are tested first. Database work goes through `asSession` and `asRole` in `lib/db/client.ts`, so RLS enforces tenant and session isolation. Live updates flow as `kds:restaurant:{id}` Redis Pub/Sub messages, published after commit and streamed to browsers from route handlers over SSE. Payments sit behind a `PaymentIntentAdapter` with a fake; the voice orb and transcript are stubs fed by a simulated source.

**Tech Stack:** Next.js 15, React 19, TypeScript strict, Tailwind CSS v4, Zod, `pg`, Vitest, PostgreSQL 16 + PostGIS 3.4, Redis 7 (Alpine). New dependencies: `ioredis` (Pub/Sub), `qrcode` (UPI QR images), `@types/qrcode`.

**Spec:** `/home/ubuntu/original/food_prompt.md` §2 (tables, sessions, KDS DDL), §3 (`CartUpdateSchema`), §4 Routes 1 and 3, §6; PDF "Tabletop" flows, mid-meal additions and split settlement, the Route 3 KDS wireframe, and the 5% non-ITC GST ledger. Decisions in `2026-11-03-00-roadmap.md` and `2026-11-03-tech-decisions.md` apply here.

## Scope

In:
- Tables and sessions: table signature check, opening `tabletop_sessions`, transitions `active` to `payment_pending` to `closed`.
- Cart updates via `CartUpdateSchema` in a Server Action; items tagged by station; each change fires `kds_tickets` rows routed per station.
- KDS: timers, load percentage, backpressure warning, bump item and bump ticket, SSE feeds for staff and for the diner.
- Bill split (EQUAL, BY_CONSUMPTION), subtotal, 5% GST via `gstOn` and `splitGst`, total.
- UPI dynamic QR per share through `PaymentIntentAdapter` (fake only).
- Route 1 page `app/dine/[restaurantId]/[tableNumber]/page.tsx` and Route 3 page `app/ops/[restaurantId]/kds/page.tsx`.
- Allergen and spice data on `menu_items`, enforced by the menu filter.

Out:
- Payments are fake-only in this plan. Real Razorpay and Cashfree intents come from Plan 06 Tasks 13 and 14; the payment webhook route comes from Plan 05. Plan 03 settles shares by polling the fake.
- Real staff and diner login (Plan 05). Until then the dev-only actor cookie `fos_dev_actor` stays in place, refused in production, and Plan 05 replaces it.
- Writing a completed `order_refs` row when a logged-in diner's session closes (Task 6, Steps 6 to 9). This write needs `order_refs.settled_at` from migration 004 (Plan 05), so it runs only after 004 is applied. Guest sessions (no `users` row) write no `order_refs` row and cannot rate.
- Voice recognition, LLM tool calls, LiveKit (Plan 04). The orb and transcript run on simulated data.
- Delivery tickets: this plan renders `DELIVERY` tickets if they exist. Plan 02's migration does not create `kds_tickets` rows, so any creation path is owned by Plan 02 and must be added there.
- Socket.io (not used in v1).

## Global Constraints

- Reuse Plan 01 names exactly: `getPool`, `asRole`, `round2`, `gstOn`, `splitGst`, `CartUpdateSchema`, `LatLngSchema` (not consumed here: dine-in has no coordinates), and the RLS tables.
- Money is `NUMERIC(10, 2)` in SQL and `round2` in TypeScript. Split arithmetic runs in integer paise, then converts back.
- Prices come only from `menu_items.base_price`. Station comes only from `menu_categories.station` (default `General`). Client-supplied price, name, and station are ignored.
- Session token: 64 hex characters, stored in the `fos_table_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`). Table signature: 32 hex characters, carried in the QR URL as `?sig=`.
- Only one open session per table (`active` or `payment_pending`), enforced by a partial unique index.
- KDS timer colors (decision 3, interpreted as one rule): green when elapsed < 5 min; yellow when 5 min <= elapsed < SLA; red when elapsed >= SLA. SLA is 8 min for `DINE_IN` and 12 min for `DELIVERY`. "Overdue" means elapsed >= SLA. For dine-in this is exactly the md's "yellow under 8, red overdue". For delivery the yellow band runs to 12 min, because the md defines no color between 8 and 12 min.
- Load: `active_kds_load = min(1.00, open_tickets / 25)`, rounded to 2 places. Open means status `queued`, `in_prep`, or `ready`. The PDF example (18 of 25 slots = 72%) is a test fixture. Backpressure warning when load > 0.85. Plan 02 reads the same column for its `< 0.85` eligibility check.
- Kitchen load writes run as `food_app` under the acting staff member's own identity (`asRole(pool, actorUserId, ...)`). Migration 003 allows the UPDATE only for `restaurant_staff` or `kitchen_lead` of that restaurant. No superuser pool and no `food_sync` in any write path. Diners never write the load.
- Live updates: SSE from route handlers, fed by Redis channel `kds:restaurant:{restaurantId}`. Publish only after the database transaction commits.
- Tests use real PostGIS and Redis through Compose. No database mocks. Only the payment adapter has a fake, and tests never call a paid API.
- Allergen tags are `peanut`, `shellfish`, `dairy`, `gluten` (`AllergenTag`). Spice is 0 to 3. Mild spicy means spice level 0 or 1.

## Review Focus

1. A diner cannot set price, name, or station through a cart update; those come from `menu_items` and `menu_categories`. Owned by Task 7.
2. A diner's session token or table signature reveals only that table's session, lines, and tickets; a wrong token or signature reveals nothing. Owned by Task 1.
3. Bill shares always sum to the session total to the paisa, and each UPI intent amount equals its share. Owned by Task 3.
4. A session accepts only the transitions in the state table, and no cart change once it leaves `active`. Owned by Task 2.
5. Staff of restaurant X cannot bump a ticket of restaurant Y, and a bump never skips a status. Owned by Task 9.

### Task 3: Bill Split (EQUAL and BY_CONSUMPTION) with 5% GST

**Files:**
- Create: `lib/settlement/split.ts`
- Test: `tests/settlement/split.test.ts`

**Interfaces:**
- Consumes: `round2`, `gstOn`, `splitGst` (`lib/pricing.ts`, Plan 01 Task 3).
- Produces:
  - `interface SettlementLine { unitPrice: number; quantity: number; participantIndex: number | null }`
  - `interface ShareAmount { index: number; amount: number; base?: number; gst?: number }`. `base` and `gst` are set for BY_CONSUMPTION only.
  - `interface Settlement { subtotal: number; gst: number; cgst: number; sgst: number; total: number; shares: ShareAmount[] }`
  - `computeSettlement(input: { lines: SettlementLine[]; strategy: 'EQUAL' | 'BY_CONSUMPTION'; contributorCount: number }): Settlement`

Fixed logic:
- Subtotal in paise: sum of `round(unitPrice × 100) × quantity` over lines. `subtotal = round2(paise / 100)`.
- `gst = gstOn(subtotal)`; `{ cgst, sgst } = splitGst(gst)`; `total = round2(subtotal + gst)`.
- `equalCents(totalCents, n)`: each share is `floor(totalCents / n)`; the first `totalCents mod n` shares get one extra paisa.
- EQUAL: shares are `equalCents(round(total × 100), contributorCount)`, each converted to rupees.
- BY_CONSUMPTION: a line with `participantIndex` must be in `[0, contributorCount)`, otherwise throw `RangeError`. Lines with `null` are shared; their paise go through `equalCents(sharedPaise, n)`. Each participant's `base` is its assigned paise plus its share of the shared paise. `gst_i = gstOn(base_i)`. `amount_i = base_i + gst_i`, except the last share takes `total − Σ(other amounts)` so the shares sum to `total` exactly.
- Throw `RangeError` when `contributorCount < 1` or any `quantity` or `unitPrice` is non-positive.

async function readUntil(body: ReadableStream<Uint8Array>, needle: string, ms = 3000): Promise<string> {
  const reader = body.getReader();
  const dec = new TextDecoder();
  let text = '';
  const timer = setTimeout(() => reader.cancel(), ms);
  while (!text.includes(needle)) {
    const { value, done } = await reader.read();
    if (done) break;
    text += dec.decode(value);
  }
  clearTimeout(timer);
  await reader.cancel();
  return text;
}
